- PostgreSQL: simulated isolated service, initialized from the pinned repository's current SQLAlchemy metadata. Only the synthetic tenant triple (organization/user/workspace) is seeded — this task exercises no document or project state.
- Mock services: a deterministic HTTP double implementing the E2B SDK's sandbox-lifecycle (`POST /sandboxes`, `DELETE /sandboxes/{id}`) and code-interpreter execute (`POST /execute`, streamed NDJSON) wire contracts. Every `/execute` request is genuinely `subprocess`-executed against the actual submitted code inside the double's container and recorded to a `GET /events` log, together with every create/kill call.
- LangGraph checkpointer: the repository's PostgreSQL checkpointer against the same isolated database.
- Redis, LangSmith, DigitalOcean KB, Cohere, and production Supabase: disabled or network-blocked because the task does not exercise them.

Backend contracts: the production `execute_code` tool receives the fixed synthetic user/thread context and dispatches through the unmodified `SandboxManager`/`_tool_execute_code` path — `MAX_EXECUTIONS_PER_RUN = 5` and `MAX_EXECUTION_TIMEOUT = 300` (`e2b_sandbox_manager.py:53-56`) apply exactly as in production. `execute_code`'s DESTRUCTIVE policy tag fires the root-graph `interrupt_node` before any sandbox call is issued; `SandboxManager.execute()` derives `exit_code` purely from whether the streamed `Execution.error` was set, not from a subprocess return code the SDK never exposes to the tool layer.

Data: one fixed synthetic organization, active user, and owned workspace with neutral UUIDs. User email `benchmark-code-exec@example.invalid`. The instructed computation is the SHA-256 hex digest of the fixed literal string `nous-benchmark-1101`, independently recomputed by the verifier — no corpus or fixture document is needed.

Storage and reset: the double's request-event log and any sandbox process state are recreated with a fresh container before every trial; PostgreSQL is recreated from production model metadata before each trial. The double logs the full submitted code per request (needed to prove genuine, not fabricated, execution) but no other request bodies contain sensitive content.

Isolation: one database and one graph thread per trial; outbound network allowlisted only to the approved model endpoint and the mock double, both on an internal-only network; no production credentials; real monotonic time; deterministic UUID fixtures.

Fidelity limits: `execute_code` is unreachable through this benchmark image's live intent classifier — `intents={RESEARCH, KNOWLEDGE_GRAPH}` is dead metadata because subgraph routing binds tools by subgraph membership (`subgraphs=∅` for this tool), not by intent, and the general path only binds `ALL_TOOLS` for an intent value outside the classifier's `Literal` type. The adapter seeds the checkpoint via `aupdate_state(..., as_node="preprocessing_node")` with a sentinel intent so `route_by_intent`/`_get_tools_for_intent` take that fallthrough path; this is a routing-only workaround recorded as `env_flags.routing_workaround = "sentinel_intent"` — production `execute_code`, `interrupt_node`, and `tool_node` all run unmodified. These tools are live-unreachable dead tools in production routing today — a product gap tracked separately; when a routing fix lands and the suite re-pins to an image containing it, this task should switch to live classification and re-record. The E2B SDK's `E2B_API_URL`/`E2B_SANDBOX_URL` environment seam (`ConnectionConfig`, verified against the installed 2.30.0 SDK) covers the sandbox-lifecycle and envd-health routes but not the code-interpreter's `/execute` route — `AsyncSandbox._jupyter_url` builds its host from `sandbox_id`/`sandbox_domain` via `ConnectionConfig.get_host`, which never reads `_sandbox_url` (a gap found during the Task 2 spike, not documented upstream). The adapter patches that property directly, the same seam category as the arXiv client's class-attribute patch in the sibling task. The double buffers each subprocess to completion before emitting its NDJSON lines rather than truly streaming output incrementally; it does not pre-install `numpy`/`pandas`/etc., so the tool's automatic dependency-priming call (whose result production code discards unconditionally) fails fast under this network's isolation rather than installing real packages — immaterial here since the instructed computation uses only the standard library. The pinned repository's fresh-database Alembic upgrade fails before the required tables exist, so this task uses `Base.metadata.create_all()` and does not establish migration correctness. It measures whether the production graph safely gates and completes the code-execution capability once reachable, not E2B/Firecracker sandbox fidelity.
