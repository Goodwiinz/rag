# Redis durability contract

Audit P1.3/P1.4 companion doc (findings X1, D7). One managed Redis instance
(DO Managed Redis in the cluster; local Redis in compose) backs several
key families with **very different durability needs**. This is the explicit
contract: what each family is allowed to assume, what happens when Redis
loses data (failover, eviction, flush), and which mechanism absorbs the loss.

Managed Redis is treated as **cache-grade, not storage-grade**: failovers can
lose recent writes and we do not control persistence settings. Anything that
must survive Redis therefore needs a Postgres projection or an explicit
fail-open/fail-closed decision, documented here.

## Rules of thumb

1. **Nothing user-owned may live only in Redis.** Status/lifecycle needs a
   Postgres projection (agent runs) or a DB row (processing jobs, chat
   messages). Redis-only data must be reconstructible or droppable.
2. **Write DB state before publishing to the broker** (flush-before-external)
   so every enqueued unit of work has a durable, sweepable record.
3. **Sweepers are the recovery half of every fire-and-forget**: if you add a
   new "enqueue and hope" path, add (or extend) a sweeper that notices the
   hope failing, and gate it behind `SWEEPERS_ENABLED`.
4. **Fail-open vs fail-closed must be an explicit, documented decision** per
   family (see CLI revocation above), never an accident of exception
   handling.
